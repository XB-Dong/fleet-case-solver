# 面向美团无人配送场景的云控故障诊断 Agent

**Fleet Case Solver 设计与实践｜面试演示版**

本项目围绕无人配送云控平台的日常值班场景，构建“数据分析、告警处理、人工取证、Agent 辅助诊断、案例沉淀”的完整演示链路。它是基于公开岗位方向独立设计的技术 Demo，不是美团内部系统或线上项目复刻。所有车辆、站点、任务与故障数据均由程序合成。

Agent 当前采用**可复现的诊断策略回放**：真实执行查询工具，根据返回证据生成分级结论；它不是已验证的大模型自主推理。模型工具调用接口已预留，但本次面试版本不依赖真实模型服务。数据链路可使用真实 MySQL、Redis、Kafka、Flink、Doris，组件状态与记录量由运行接口查询，而不是写死在页面上。

---

## 一 为什么要做这件事

无人车云控系统的异常常常跨越多条链路：

```text
配送任务 → 站点运力筛选 → 路线与准入检查 → 派单
    → 车辆执行 → 心跳与遥测 → 指标聚合 → 告警
```

运营看到的往往是“任务一直积压”“一批车辆突然离线”“这个站点派不出车”。但相同现象可能有完全不同的原因：车辆真实离线、状态数据陈旧、路线缓存失效、准入配置变化、数据消费积压，都可能表现为可用运力下降。

单看一个看板无法回答“为什么”。排查需要把业务库、遥测数仓、服务日志、缓存状态、配置审计和代码行为串起来。

### 1.1 人工排查中的典型问题

- **路径依赖经验。** 资深同学知道先看哪个指标、哪张表，新同学容易从日志开始漫无目的地查。
- **指标口径容易混淆。** “真实心跳在线”“遥测看板在线”“具备可调度资格”不是同一个指标。
- **异常与影响存在时间差。** 服务报错时业务可能仍靠旧缓存维持，真正的派单失败要等到缓存过期才出现。
- **证据散落在不同页面。** SQL、日志、接口响应和代码截图没有统一关联，复盘时难以复现。
- **历史经验难复用。** 上次排查结论留在聊天里，下次遇到相似问题仍然重走全程。

### 1.2 项目目标

把高频 Oncall 问题变成“有统一入口、有真实证据、有明确边界、可复盘”的排障流程。首先让人工能够完整排查，再把同一套工具暴露给 Agent，使自动诊断的每一步都能被人工复核。

项目不控制真实车辆，不实现自动驾驶感知、规划或远程接管。关注的是云控平台的运营工具、数据分析和研发值班效率。

## 二 设计思路

### 2.1 先让问题可复现 再讨论自动诊断

Demo 里的故障不是“点按钮后把看板数值改红”。以路线同步异常为例，程序会真正执行有缺陷的函数，抛出数组越界异常；缓存刷新失败后继续保留旧值，待有效期耗尽，可调度车辆才下降。

这样，前端指标、数据库记录、错误日志、接口原始响应和代码行为来自同一条因果链。人工和 Agent 查询的是相同现场，便于对照结论。

### 2.2 区分诊断流程和执行约束

流程负责引导“先理解什么，再验证什么”；执行层负责控制“能调用什么，能访问哪些数据”。不能仅在提示词里写“请勿改数据库”，就认为完成了只读约束。

| 层次 | 职责 | 本项目的具体做法 |
| --- | --- | --- |
| 业务流程 | 分类、检索、假设、取证、验证、结案 | 七步诊断约定 |
| 工具接口 | 把系统能力变成可调用的证据入口 | SQL、指标、日志、缓存、配置、代码、Doris 查询 |
| 执行层 | 权限、范围、时限、结果上限 | 只读连接、工具白名单、SQL 检查、站点与时间隔离 |
| 输出层 | 让结论可以核对 | 事实、推断、待确认、已排除与建议分开 |
| 知识层 | 把一次排查变成后续参考 | Case JSON、Markdown、历史检索 |

### 2.3 两种运行方式必须明确区分

**确定性回放。** 根据工具返回的指标和拒绝原因选择排查分支；能够稳定演示工具链、证据等级与案例沉淀。它不会直接读取模拟器的故障标签来决定答案，但诊断分支本身是预先实现的。

**模型工具调用。** 模型读取诊断约定和工具描述，自主选择白名单工具；服务执行工具并把结果送回模型，最多迭代 18 轮。接口协议与证据引用检查已通过模拟端点测试，但未开展真实模型的根因准确率评测。

面试时应明确说：“我完成了工具执行层和可复现诊断闭环，当前用策略回放保证演示稳定；模型接口已经留好，真实模型的效果需要另做评测。”

### 2.4 相似案例复用路径 不直接套结论

“车辆在线但派不出任务”既可能是路线失效，也可能是电量阈值上调。仅凭现象相同，不能复用上次的根因。

每次运行记录站点、事件时间窗口和现场版本。历史案例可以提示优先查询什么，但当前结论必须重新取证。若诊断期间模拟时钟或故障现场变化，执行层拒绝继续混用证据，要求重新诊断。

## 三 业务场景与数据底座

### 3.1 数据规模与对象

默认生成 300 辆无人配送车、6 个站点、14 天历史。历史遥测每五分钟一条，合计 1,209,600 条；历史任务 16,800 个。运行模拟后，会继续生成调度尝试、任务状态和分钟级遥测。

这些是实际入库的合成记录，不是数据库容量或生产性能的证明。页面展示实际记录数和查询耗时。

| 对象 | 用途 | 关键关联字段 |
| --- | --- | --- |
| 车辆 | 电量、真实心跳、可调度状态、位置示意 | vehicle_id、station_id |
| 配送任务 | 创建、完成、超时或积压 | task_id、vehicle_id、trace_id |
| 调度尝试 | 成功或被拒绝的原因 | task_id、reason、trace_id |
| 遥测事件 | 时序状态与数据新鲜度 | event_time、ingest_time、event_id |
| 配置审计 | 事发时的历史配置变化 | config_key、old_value、new_value |
| 告警工单 | 认领、处理、恢复与结案 | alert_id、owner、status |

### 3.2 技术栈及分工

| 技术 | 在演示中的分工 | 设计理由 |
| --- | --- | --- |
| React TypeScript ECharts | 云控工作台、趋势与查询交互 | 方便做指标下钻和工具结果展示 |
| Python FastAPI | 故障模拟器、诊断工具与 Agent 执行层 | 便于构建可控现场和工具适配 |
| SQLite | 本地合成数据与可重复故障事实 | 保障不依赖集群也能演示 |
| Java Spring Boot | 读取真实 MySQL 与 Redis 的业务查询服务 | 展示云控业务服务的常见工程组织 |
| MySQL | 车辆与最新任务快照 | 保存结构明确的业务对象 |
| Redis | 路线状态及真实 TTL | 展示短期状态和缓存有效期 |
| Kafka | 遥测原始流与清洗结果流 | 解耦生产与消费，支持回放 |
| Flink SQL | 清洗、延迟计算、事件时间窗口 | 展示实时数据处理与水位线 |
| Doris | 清洗遥测明细、站点分钟汇总 | 支撑大量明细上的交互式分析 |
| Prometheus Alertmanager Grafana | 真实监控与告警（可选启用） | 将业务指标接入监控与告警体系 |

这是根据场景需要选择的 Demo 技术栈。公开技术文章可以支持选型合理性，不能据此推断美团无人车内部的具体部署。

### 3.3 完整数据路径

```text
合成车辆与任务
    ├── 本地模拟器 → 指标 / 日志 / 配置 / 人工排查
    ├── 快照复制 → MySQL / Redis → Java 查询服务
    └── 遥测事件 → Kafka 原始主题
                    → Flink 清洗与窗口计算
                    → Kafka 清洗主题与分钟主题
                    → Stream Load
                    → Doris 明细表与汇总表
```

SQLite 在这里充当可控的事件发生器与轻量运行底座；Doris 中的数据必须经过实际消息与流计算链路才能出现。数据工作台明确选择数据源，真实组件不可用时返回错误，不悄悄回退到 SQLite 后仍标成 Doris。

## 四 Agent 功能模块

### 4.1 七步诊断流程

| 步骤 | 要完成的事 | 关键产物 |
| --- | --- | --- |
| 第零步 分类 | 确定站点、时间窗口、异常现象与影响对象 | 当前排查范围 |
| 第一步 检索 | 查询历史案例，识别可参考路径 | 相似案例线索 |
| 第二步 理解 | 区分真实在线、可调度与遥测新鲜度 | 对问题的业务解释 |
| 第三步 规划 | 优先验证低成本且区分度高的假设 | 取证顺序 |
| 第四步 取证 | 查指标、SQL、日志、接口、缓存、配置和代码 | 带编号的工具结果 |
| 第五步 验证 | 连接异常、状态变化与业务结果 | 分级根因结论 |
| 第六步 沉淀 | 保存结论、范围、证据、耗时与建议 | 可下载的案例文档 |

流程不意味着所有故障都要机械调用同一组工具。比如数据延迟案例，先比较实时心跳与看板新鲜度，就能够排除“车辆真实批量离线”；没有必要先翻路线代码。

### 4.2 工具层

| 工具 | 解决的问题 | 边界 |
| --- | --- | --- |
| get_data_context | 表有哪些字段，指标是什么意思 | SQL 前先读取 |
| query_sql | 当前窗口主要发生了什么 | 只读、站点与时间隔离、返回上限 |
| query_metrics | 真实心跳、可调度、积压与延迟是否一致 | 指标口径明确 |
| query_logs | 哪个服务何时发生异常 | 按站点与当前事件窗口查询 |
| get_route_payload | 上游原始响应是否符合预期 | 读取原始结构，不只看计数 |
| inspect_cache | 模拟现场路线状态是否过期 | 显式标记模拟时钟 TTL |
| config_diff | 配置何时从什么值变成什么值 | 历史审计优先于当前值 |
| read_registered_code | 系统为什么做出该行为 | 仅读取登记文件 |
| query_warehouse | 真实 Doris 能否看到该窗口的遥测 | 固定范围模板，标记真实数据源 |
| inspect_live_cache | 真实 Redis 中是否有对应路线和 TTL | 墙上时钟与模拟时钟分开 |
| check_data_pipeline | 真实组件连通性与 Flink 作业状态 | 连接成功不等于业务正确 |
| search_cases | 之前是否处理过相关问题 | 只复用路径，重新核验事实 |

MCP 对外提供数据上下文和统一 `investigate` 入口；客户端传入工具名及站点。网页与 MCP 复用服务端实现。

### 4.3 两条互补的证据路径

**数据路径回答发生了什么。** 哪个站点出现下降、从何时开始、影响多少车、拒绝原因占比多少、数据是否延迟。

**机制路径回答为什么会这样。** 原始响应是什么结构、缓存为什么没有续期、配置为什么过滤了这些车、异常是否发生在整批提交之前。

两条路径需要互相校验。例如只看到 `ROUTE_EXPIRED`，可以证实路线状态过期，但不能直接断言同步程序有数组越界；必须补看日志、接口和代码。

### 4.4 证据分级

- **已验证事实：** 工具结果可以直接支持的内容，例如错误日志、空路线数组、过期车辆数量、配置变更记录。
- **合理推断：** 多个事实共同支持，但尚未通过独立实验完全证实的机制，例如连续批次失败导致旧缓存未续期。
- **待确认：** 工具不可达或当前证据不足的问题，说明下一步需要什么材料。
- **已排除：** 有证据反驳的假设，例如实时心跳正常时，不支持车辆真实批量离线。

输出中的 `[E01]`、`[E02]` 对应实际工具调用。编号存在只是必要条件；它不自动证明模型的语义解释正确。因此保留人工复核入口。

### 4.5 只读与隔离

轻量查询使用 SQLite 只读连接、authorizer、执行超时与返回行数限制。Agent 的通用 SQL 查询在当前站点和事件窗口的数据副本上执行，防止无意跨范围读取。

真实 MySQL 和 Doris 使用专门的 SELECT 账号，同时解析 SQL，拒绝写语句、多语句、未登记表、跨库读取、文件导出和高风险函数。真实 Doris 取证工具进一步使用固定站点与时间模板。

Agent 不能点击恢复按钮、修改运力阈值、删除数据或发布正式规则。恢复动作由演示控制台执行，再通过后续指标验证结果。

## 五 三个演示案例

### 5.1 主案例 车辆在线但站点派不出任务

**原始问题示例**

> 南山站点任务开始积压，车还是在线的，为什么派不出去？

**故障机制**

```text
一条路线记录的 routes 为空
    → 同步函数直接读取首元素
    → 异常发生在批次缓存提交之前
    → 本批路线没有完成刷新
    → 旧缓存继续维持一段时间
    → 600 秒有效期耗尽
    → 车辆仍在线，但不满足路线准入
    → ROUTE_EXPIRED 拒绝增加
    → 积压出现并触发告警
```

在默认配置下，该站点有 50 辆车。故障注入初期旧缓存仍有效；推进约十分钟后，站点可调度数降为 0。六站点合计仍有 300 辆真实在线车辆，但可调度车辆从 300 降为 250。

**取证顺序**

1. 比较真实心跳与可调度数，排除直接将问题解释为掉线。
2. 聚合调度拒绝原因，发现集中在 `ROUTE_EXPIRED`。
3. 查同步服务日志，发现数组越界和批次提交中断。
4. 查原始路线响应，确认存在空数组。
5. 查缓存 TTL，确认影响范围与不可调度范围吻合。
6. 阅读登记代码，定位首元素访问及批次提交的位置。
7. 在沙箱恢复数据与刷新逻辑，核验拒绝下降、运力回升、积压清理与告警恢复。

**示例结论**

> 业务结论：车辆心跳正常，站点的路线状态失效使车辆无法进入派单候选，导致任务积压。
>
> 技术结论：当前证据包含同步异常日志、空路线响应、过期缓存和代码提交位置。它们支持“异常中断批次刷新，旧缓存到期后影响派单”的解释。修复应包括空数组检查和异常记录隔离，并验证正常记录仍可刷新。
>
> 恢复验证：可调度车辆恢复，拒绝原因消失，积压下降；工单记录验证结果后关闭。

这个案例的价值在于展示“异常发生时间”和“业务损失出现时间”之间的缓存延迟，而不是只展示一个错误码。

### 5.2 反例 看板离线不等于车辆离线

模拟遥测消费停止后，数据新鲜度逐步恶化。超过 180 秒，看板可能把车辆判为离线，但实时心跳仍正常，派单也未必失败。

排查时先比较真实心跳、遥测最新事件时间和业务成功率。当前工具可以支持“数据陈旧造成离线假象”，但没有消费者进程或分区级证据时，不能编造具体 Kafka 分区或网络设备故障。

这个案例用于验证 Agent 是否会把一个可见症状过度解释成确定根因。

### 5.3 配置案例 电量准入阈值上调

模拟把最低电量要求从 20 调到 92。一批正常在线车辆因此被筛掉，`BATTERY_POLICY` 拒绝增加，任务积压。

需要把拒绝原因与配置审计中的变更时间、前后值对应起来。当前配置不能单独证明事故发生时的配置，更不能说明变更意图。

建议确认策略意图后在沙箱回退，并对照派单成功率和积压验证恢复。不能用“改回去了”代替“已经验证业务恢复”。

### 5.4 联调实录 Doris 写入停滞

这不是预设的业务故障，而是本次实际运行百万条回灌时遇到的问题，可以作为数据链路排障的补充案例。

**现象：** Flink 作业仍在 RUNNING，Kafka 已收到原始数据，Doris 明细停在约 98 万条。可见“进程在线”和“端到端数据完整”是两件事。

**取证：** 对比源端与 Doris 的 COUNT；查看 Stream Load 响应发现 tablet version 达到 2000；继续检查 compaction，发现合并任务因内存限制失败。单看 Flink 作业状态无法定位这个问题。

**处理：** 将每批最多 500 条提高到 5000 条，减少小批次写入产生的版本；为实验 Doris 调整 BE 与容器内存，触发合并，等待消费继续推进。没有跳过失败记录，也没有把未完成的回灌标为成功。

**验证：** 初始明细最终为 1,209,900 条，与源端一致；分钟窗口累计事件为 1,209,600，符合已关闭历史窗口口径；故障与恢复新增数据也继续写入，最终明细为 1,214,700 条。

**面试延伸：** 数据量不大也可能因为写入模式造成数据库压力。应同时看吞吐、批次大小、版本数、合并资源、消费位点和数据新鲜度；不能把扩大内存当作所有积压问题的统一答案。当前 Agent 还没有自动诊断这个基础设施故障，以上链路由联调过程人工完成。

## 六 告警与人工 Oncall

### 6.1 生命周期

```text
待认领 → 排查中 → 已恢复 → 已关闭
```

认领需要负责人；排查过程可记录备注；业务指标恢复后才允许关闭；结案必须填写结论。告警恢复和积压归零是两个条件，演示中需要继续推进时间核验后者。

### 6.2 人工排查工作台

人工工作台把指标、拒绝原因、日志、原始接口、缓存、配置和代码放在同一现场范围内。每次点击真实执行查询，展示返回内容和耗时。

人工 SOP 的作用是避免漏项，不能代替判断。比如缓存未过期时应继续观察，而不是因为已经看到同步异常，就声称业务损失已经发生。

### 6.3 人工与 Agent 的关系

人工路径用于建立可信基线，Agent 路径用于复用工具与流程。两者应当能解释同一现场，并且能指出各自缺少哪些证据。

在面试中可以先用两分钟手动找出根因，再运行回放，逐项对照工具结果。不要仅展示 Agent 的一句最终回答。

## 七 案例沉淀与知识治理

每次诊断保存一份 JSON 和一份 Markdown。记录包括问题、站点、时间范围、模式、工具参数与结果、证据编号、实际耗时、分级结论和建议动作。

```text
data/cases/
    <case_id>.json    完整运行证据
    <case_id>.md      可阅读的结案说明
```

运行数据默认只保存在本地，不进入公开 Git。正式公开仓库只保留独立代码、合成数据生成器、通用流程与说明文档。

案例复盘后，可以提出候选规则，例如“看到大批车辆离线，先核查数据新鲜度”“配置问题必须看历史审计”。候选规则需要人工审核，再进入正式 SOP；当前版本不会让模型自动改写长期规则。

后续可加入案例索引、标签与语义检索。语义相似用于找线索，事实复用仍需要严格核验对象与时间范围。

## 八 接入方式与项目组织

### 8.1 网页值班台

适合现场演示：选择站点、注入故障、推进模拟时钟、认领告警、人工取证、运行回放、恢复和结案。数据工作台可切换 SQLite、MySQL 与 Doris，并显示实际来源和耗时。

### 8.2 MCP 接入

适合 Coding Agent 调用现成只读工具。启动本地服务后运行 `agent/mcp_server.py`，通过 stdio 暴露数据上下文和统一取证入口。此入口不提供故障注入或恢复操作。

### 8.3 代码组织

```text

backend/database.py     轻量数据库与数据生成

services/business/     Java 业务查询服务
tests/                 故障 隔离 协议与规模回归
```

## 九 验证方法与能力边界

### 9.1 应当验证什么

| 维度 | 检查方法 | 不能替代它的证据 |
| --- | --- | --- |
| 故障真实性 | 程序产生异常与业务状态变化 | 页面颜色变红 |
| 数据链路 | Kafka 主题、Flink 作业、Doris 实际行数与聚合 | 容器显示 running |
| 根因闭环 | 指标、日志、状态和代码相互支持 | 仅命中历史案例 |
| 隔离 | 修改站点后重新查询，拒绝越界 SQL | 提示词写“只读” |
| 恢复 | 拒绝消失、运力回升、积压下降 | 仅执行恢复动作 |
| 模型能力 | 独立测试集、真实模型运行、人工判定 | 策略回放速度 |

2026-11-07 实测：初始 1,209,900 条遥测经过 Kafka / Flink 落入 Doris，与源端行数一致；主案例 Agent 完成 10 次取证，真实查询 Doris 与 Redis，告警到达 Alertmanager，恢复后 300 辆可调度、积压归零。详细结果见 [验证记录](validation.md)。测试数量与运行数据以这些记录和当前接口为准，不把未来设计写成已经上线的成果。

### 9.2 当前明确的边界

- Agent 当前展示的是确定性回放，不声称已经完成真实模型诊断评测。
- 完整栈仍是本地实验，单节点组件不等于生产高可用架构。
- MySQL 任务是最新快照复制，不是完整 CDC；Redis 使用墙上时钟 TTL，与模拟时间分别标注。
- Kafka 到 Doris 链路按至少一次投递设计，明细唯一键支持重复覆盖；窗口聚合不能自动等同于端到端精确一次。
- 流处理模式保持事件时间单调递增，切换故障先恢复，避免重置时钟破坏 Flink 水位线。
- 当前 trace_id 是业务关联键；不把它包装成已经完成分布式 OTel 全链路观测。
- 没有真实车队、线上工单、内部系统地址或企业私有数据。

## 十 后续演进

**近期补齐工具。** 增加消费者分区积压、Flink checkpoint 与反压、历史配置版本、数据库慢查询，减少“知道数据有问题但无法进一步定位”的断点。

**中期验证模型。** 准备正常场景、不同根因的相似现象、证据缺失、历史案例误导、工具超时等评测集；比较根因正确率、证据完整性、无依据结论比例、工具次数、延迟和真实 token 成本。

**长期治理知识。** 将病例检索、规则审批、版本管理和回归测试连接起来。每次新增排查模式，都用旧案例验证没有引入新的误判。

## 十一 面试表述建议

可以这样概括：

> 我针对无人配送云控的 Oncall 场景，做了一个可复现的全栈排障 Demo。它有百万级合成遥测、三类故障和完整工单流程。人工和 Agent 共用只读工具，从指标、日志、缓存、配置和代码建立证据链。为了让演示稳定，Agent 目前采用策略回放，模型接口已经预留；大数据链路则通过实际组件和查询结果验证。项目重点是诊断工具与执行约束，不是宣称已经在真实车队上线。

遇到“为什么不直接用一个大模型”时，可以回答：

> 模型能选择排查路径，但不能替代数据访问、指标口径和权限隔离。先建立可验证的工具层和回归案例，才有条件评测模型是否提高了诊断质量。

遇到“与普通问答知识库有什么区别”时，可以回答：

> 知识库告诉我过去怎么排查，工具告诉我当前发生了什么。当前证据和历史线索必须分开，否则很容易用一个相似案例套错根因。
