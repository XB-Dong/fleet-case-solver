# 10 分钟演示讲稿

## 0:00–1:00 讲清场景

“这是一个无人配送云控实验。我要解决的不是驾驶决策，而是运营与研发值班：业务指标异常时，如何从大量车辆与任务数据找到原因，并将经验转为可复用工具。”

展示实际 300 辆车、6 个站点和百万级遥测。说明数据为合成、当前为 Lite 模式、完整组件配置未在此电脑验证。

## 1:00–2:00 查看数据底座

打开数据目录，查看 vehicles、tasks、telemetry、dispatch_attempts。执行聚合 SQL，指出实际耗时、返回行数、event_time 与 ingest_time 的区别。展示 trace_id 如何关联任务和调度日志。

## 2:00–3:00 注入并观察

注入路线故障。第一分钟不一定影响业务，因为旧缓存仍有效。推进十分钟后，部分站点可调度数下降，但真实车辆心跳正常。

“延迟出现的业务影响来自缓存有效期；错误时间和告警时间不同，这一点决定排查窗口不能只看告警之后。”

## 3:00–5:00 手工排查

认领告警，沿 SOP 查询拒绝原因、异常日志、原始 API、缓存 TTL、代码。把“看到派单失败”推进为“解释失败的机制”。证据不足时保留待确认，不将相关性当成已证实因果。

## 5:00–7:00 Agent 对照

运行确定性回放，明确告知面试官这不是 LLM 模式。展开工具轨迹，说明 Agent 和人工用相同数据，结论可追溯。若本地已配置模型，可改用真实工具调用并展示实际 token 与耗时。

“通用流程不需要为每种业务重写。迁移时需要替换实体分类、工具适配、指标语义与知识模式；权限和证据约束应该在执行层实现，而不只写在提示词里。”

## 7:00–8:00 恢复与沉淀

恢复沙箱，再推进几分钟看积压清理。填写结案记录，关闭工单，打开生成案例和 Markdown。解释历史案例只能提供排查路径，不能跨站点、跨时间直接套用结论。

## 8:00–9:00 展示反例

重置，注入遥测延迟，推进四分钟。看板离线而真实心跳正常。Agent 应明确数据陈旧，并承认无法凭现有工具确认消费者内部原因。

## 9:00–10:00 讨论工程取舍

- 为什么 MySQL 与 Doris 分工？事务对象与分析扫描的负载不同。
- 为什么需要 Redis TTL 的证据？当前状态只显示结果，过期机制解释延迟影响。
- 为什么不是只做 RAG？案例检索只能提供线索，当前事实来自工具查询。
- 如何避免越权 SQL？只读连接、authorizer、范围隔离、超时与结果限制。
- 本地与完整栈差异？Lite 保证演示可运行，Full lab 是待联调的可选组件；不夸大完成度。
- 怎样评估 Agent？测根因正确性、证据完整性、误判率、工具耗时与调用数；本项目不编造提效比例。
